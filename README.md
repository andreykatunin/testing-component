# Qwen Code + OpenSpec: аналитика и QA без лишней бюрократии

Стартовый набор для трёх Qwen Code субагентов и OpenSpec-процесса:

```text
proposal → business-requirements → system-requirements
         → specs → design → test-cases → tasks → apply
```

Главный принцип: каждый артефакт отвечает на свой вопрос и содержит только сведения,
которые влияют на требования, реализацию или проверку.

## Роли

- `business-analyst` уточняет потребность и изменяет только `business-requirements.md`;
- `system-analyst` выводит системные требования из согласованных бизнес-требований и
  изменяет только `system-requirements.md`;
- `qa-engineer` проектирует проверки и изменяет только `test-cases.md`;
- основной агент ведёт proposal, specs, design, tasks, реализацию и сквозные связи.

Все субагенты настроены на модель:

```yaml
model: deepseek-v4-flash
```

## Что внутри

```text
.qwen/agents/                         роли субагентов
openspec/schemas/analysis-driven/     схема и семь шаблонов
openspec/config.example.yaml          контекст, project rules и operations
AGENTS.md                             правила диалога и оркестрации
```

Правила разделены по ответственности:

| Файл | Что в нём находится |
|---|---|
| `.qwen/agents/*.md` | Метод работы роли, границы ответственности, запрет домысливания и формат вопросов. |
| `schema.yaml` | Контракт артефакта, зависимости, вызов роли, согласование и критерии готовности. |
| `AGENTS.md` | Диалог основного агента с оператором и переходы между артефактами. |
| `templates/*.md` | Структура сохраняемого документа. |
| `openspec/config.yaml` | Контекст, дополнительные правила артефактов и operations конкретного проекта. |

## Установка

Нужны Node.js 20.19+ и актуальные OpenSpec и Qwen Code.

```bash
openspec init --tools qwen
openspec config profile
openspec update
```

Затем:

1. Скопируйте набор в корень проекта.
2. Объедините `openspec/config.example.yaml` с `openspec/config.yaml` и установите
   `schema: analysis-driven`.
3. Если в проекте уже есть `AGENTS.md`, объедините его с файлом из набора,
   не перезаписывая существующие проектные правила.
4. Перезапустите Qwen Code и проверьте роли через `/agents manage`.
5. Проверьте схему:

```bash
openspec schema validate analysis-driven
openspec schema which analysis-driven
```

Если provider требует квалифицированное имя модели, замените `deepseek-v4-flash`
во всех `.qwen/agents/*.md` на доступный ему model ID.

## Интерактивный протокол

Proposal, business requirements, system requirements и test cases создаются в два прохода:

```text
анализ без изменения файла
├── вопросы оператору → ответы → повторный анализ
└── проект артефакта → подтверждение оператора
                                ↓
                  отдельное задание на запись
```

В первом задании основной агент явно запрещает субагенту изменять файл. После
подтверждения он повторно вызывает того же субагента и просит записать только
согласованный проект. Предложение или рекомендация модели не становится требованием
без явного ответа оператора. Важный ответ сохраняется в требовании и в колонке
`Ответ / решение` соответствующего вопроса.

## Быстрый старт

### 1. Explore и новый change

```text
/opsx:explore
```

Основной агент отделяет подтверждённые факты от вопросов и предложений. Когда проблема,
результат и границы понятны:

```text
/opsx:new add-example-feature
```

### 2. Proposal

```text
/opsx:continue add-example-feature
```

Основной агент задаёт недостающие вопросы, показывает проект и создаёт `proposal.md`
только после подтверждения оператора.

### 3. Business requirements

```text
/opsx:continue add-example-feature
```

Основной агент просит `business-analyst` провести анализ без изменения файла,
передаёт его вопросы оператору и показывает проект `BR-*`/`AC-*`. После согласования
субагент получает отдельное задание записать требования:

```markdown
> **Статус:** Approved
>
> **Approved by:** <имя или роль>
```

Это первая формальная контрольная точка со статусом в документе. Системный аналитик
не должен додумывать несогласованные бизнес-требования.

### 4. System requirements

```text
/opsx:continue add-example-feature
```

`system-analyst` сначала исследует репозиторий. Неизвестные решения возвращаются как
`SQ-*`; числовые NFR без источника не создаются. Перед записью оператор видит
трассировку `BR/AC → SR/NFR` и подтверждает предложенные системные требования.

Перед specs убедитесь, что выполнена контрольная точка требований, описанная ниже.

### 5. Specs и design

```text
/opsx:continue add-example-feature
/opsx:continue add-example-feature
```

Specs описывают наблюдаемое поведение через OpenSpec Requirement и `SC-*`. Design
содержит только решения и ограничения, которые действительно нужны для реализации.
Неприменимые разделы можно удалить или отметить `N/A`.

### 6. Test cases

```text
/opsx:continue add-example-feature
```

Основной агент вызывает `qa-engineer` по тому же циклу анализа, согласования и записи.
Каждый `TC-*` хранит приоритет, тип, `Refs`, шаги и ожидаемый результат. Поля
автоматизации заполняются только когда они известны.

### 7. Tasks и apply

```text
/opsx:continue add-example-feature
```

Для обычной задачи обязательны только:

```markdown
- [ ] TASK-001 — Реализовать изменение
  - **Refs:** SR-001, TC-001
  - **Verify:** команда или наблюдаемая проверка
```

`Depends on` и `Done when` добавляются только там, где они дают полезное уточнение.
После review плана установите:

```markdown
> **Readiness:** Ready
>
> **Reviewed by:** <имя или роль>
```

Это вторая формальная контрольная точка со статусом в документе. Затем:

```text
/opsx:apply add-example-feature
/opsx:verify add-example-feature
/opsx:sync add-example-feature
/opsx:archive add-example-feature
```

`sync` можно пропустить, если delta specs синхронизируются во время archive.

## Контрольные точки

Перед specs основной агент и оператор проверяют:

- наличие первых трёх артефактов;
- согласование business requirements;
- отсутствие блокирующих `BQ-*` и `SQ-*`;
- наличие ответа у вопросов со статусом `Resolved`;
- отсутствие оставшихся значений из шаблона.

Перед apply дополнительно проверяют:

- наличие specs, design, test cases и tasks;
- `Readiness: Ready` и `Reviewed by`.

Контрольные точки намеренно не заменяют review качества требований, покрытия, ссылок
и сценариев: за это отвечают шаблоны, роли и оператор.

## Глоссарий ID

### Business requirements

| ID | Значение | Когда использовать | Типичная связь |
|---|---|---|---|
| `BR-*` | Business Requirement | Требование бизнес-уровня. Тип `Functional` описывает необходимое поведение продукта, `Rule` — бизнес-правило или запрет, `Constraint` — существенное ограничение. | Служит источником для `AC-*`, `SR-*`, `NFR-*` и specs. |
| `AC-*` | Acceptance Criterion | Конкретный бизнес-пример, по которому можно принять результат. Обычно оформляется как Given/When/Then. | Ссылается на один или несколько `BR-*`; далее покрывается `SC-*` и `TC-*`. |
| `BQ-*` | Business Question | Неопределённость о цели, scope, правиле или ожидаемом поведении, которую должен разрешить владелец бизнеса. | При `Блокирует: Да` останавливает переход к системному анализу. |

Тип `BR-*` выбирается по смыслу:

- `Functional` — действие пользователя или наблюдаемое поведение продукта;
- `Rule` — условие, политика, разрешение или запрет;
- `Constraint` — внешнее ограничение, которое необходимо соблюдать.

```text
BR-001 Functional: клиент может посмотреть текущий статус заказа.
BR-002 Functional: клиент получает уведомление при изменении статуса.
BR-003 Rule: клиент может видеть только собственные заказы.
BR-004 Constraint: история статусов хранится не менее одного года.
```

Проблема, бизнес-цель и ожидаемый результат не дублируются отдельными требованиями:
они уже зафиксированы в proposal и разделе «Контекст и цель».
Если ограничение обязательно должно быть выполнено и проверено, оно получает `BR-*`
с типом `Constraint`; обычное допущение остаётся в разделе ограничений и допущений без ID.

### System requirements

| ID | Значение | Когда использовать | Типичная связь |
|---|---|---|---|
| `SR-*` | System Requirement | Проверяемое требование к системе. API, события, данные, валидации, ошибки, безопасность, наблюдаемость и миграции различаются значением `Тип`, а не отдельными ID. | Выводится из `BR-*` или `AC-*`; уточняется в specs/design и проверяется `TC-*`. |
| `NFR-*` | Non-functional Requirement | Измеримое требование к производительности, надёжности, безопасности или другому качественному свойству. | Имеет бизнес- либо техническое основание; проверяется отдельным `TC-*` или указанной метрикой. |
| `SQ-*` | System Question | Неопределённость о текущей системе, контракте, данных или техническом ограничении. | При `Блокирует: Да` останавливает переход к specs/design. |

### Specs, QA и implementation

| ID | Значение | Когда использовать | Типичная связь |
|---|---|---|---|
| `SC-*` | OpenSpec Scenario | Один наблюдаемый пример поведения внутри OpenSpec Requirement в формате Given/When/Then. | Выводится из `AC-*`/`SR-*`; покрывается одним или несколькими `TC-*`. |
| `TC-*` | Test Case | Воспроизводимая проверка с предусловиями, данными, шагами и ожидаемыми результатами. | В `Refs` указывает `AC-*`, `SR-*`, `NFR-*` или `SC-*`; может быть связан с `TASK-*`. |
| `QA-Q-*` | QA Question | Неопределённость, из-за которой QA не может однозначно определить ожидаемый результат или способ проверки. | Возвращается владельцу исходного требования; может блокировать связанный `TC-*`. |
| `TASK-*` | Implementation Task | Атомарная работа по реализации, проверке, миграции или выпуску. | В `Refs` указывает требования, сценарии и тест-кейсы; содержит наблюдаемый `Verify`. |

Обычная сквозная связь:

```text
BR → AC → SR/NFR → OpenSpec Requirement + SC → TC → TASK
```

Допустимы связи через несколько уровней и несколько источников. Например, один `AC-*`
может уточнять несколько `BR-*`, а один `TC-*` — проверять связанные `AC-*`, `SR-*`
и `SC-*`.

### Общие поля

| Поле | Назначение |
|---|---|
| `OpenSpec change` | ID change, которому принадлежит документ. |
| `Refs` | Список стабильных ID, из которых выведен элемент или которые он покрывает. |
| `Источник` | Человек, документ, политика или подтверждённый факт, из которого получено требование. |
| `Тип` | Классификация элемента без создания дополнительного семейства ID. |
| `Приоритет` | Важность требования или теста, а не порядок его реализации. |
| `Проверка` / `Verify` | Наблюдаемый способ доказать выполнение требования или задачи. |
| `Статус` | Состояние конкретного документа, вопроса или тест-кейса; допустимые значения задаёт его шаблон. |
| `Ответ / решение` | Подтверждённый ответ оператора или владельца требования на открытый вопрос. |
| `Approved by` | Кто явно согласовал бизнес-требования. |
| `Readiness` / `Reviewed by` | Готов ли план к apply и кто это подтвердил. |
| `Automation Reference` | Ссылка на существующий автоматизированный тест. |

ID остаются стабильными: их не перенумеровывают, не переиспользуют и не меняют при
перемещении элемента. Удалённый тест-кейс помечается `Deprecated`. Все связи между
артефактами указываются через `Refs` или колонку источника.

## Как не потеряться в начале

- Берите один небольшой change и используйте пошаговый `/opsx:continue`.
- Не заполняйте секцию «на будущее»: удалите её или поставьте `N/A`.
- В вопросах оставляйте только то, без чего нельзя продолжить.
- Сначала добейтесь связной цепочки `BR → SR → SC/TC → TASK`, затем добавляйте детали.
- Используйте `/opsx:ff` только когда структура стала привычной.

Именованные субагенты не наследуют контекст друг друга: каждый заново читает change,
нужные upstream-артефакты и релевантный код. Основной агент отвечает за повторный запуск
downstream-роли после изменения требований.
