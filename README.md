# Qwen Code + OpenSpec: аналитика и QA

Стартовый набор добавляет в проект трёх Qwen Code субагентов и пошаговый
OpenSpec-процесс:

```text
proposal → business-requirements → system-requirements
         → specs → design → test-cases → tasks → apply
```

`business-analyst`, `system-analyst` и `qa-engineer` анализируют принадлежащие им
артефакты. Основной агент управляет OpenSpec, передаёт вопросы и ответы и создаёт
остальные артефакты.

## Что входит в набор

```text
.qwen/agents/                         субагенты аналитики и QA
openspec/schemas/analysis-driven/     схема процесса и шаблоны
openspec/config.example.yaml          пример настройки проекта
AGENTS.md                             правила оркестрации
```

| Артефакт | Автор | Назначение |
|---|---|---|
| `proposal.md` | основной агент | Проблема, ожидаемый результат и scope. |
| `business-requirements.md` | `business-analyst` | Бизнес-требования и критерии приёмки. |
| `system-requirements.md` | `system-analyst` | Проверяемые требования к системе. |
| `specs/**/*.md` | основной агент | Delta-спецификации наблюдаемого поведения. |
| `design.md` | основной агент | Существенные технические решения. |
| `test-cases.md` | `qa-engineer` | Трассируемое тестовое покрытие. |
| `tasks.md` | основной агент | План реализации и проверки. |

## Требования

- Node.js 20.19 или новее;
- установленный Qwen Code;
- актуальный OpenSpec.

Установка OpenSpec:

```bash
npm install -g @fission-ai/openspec@latest
```

## Подключение к проекту

### 1. Инициализируйте OpenSpec

В корне целевого проекта выполните:

```bash
openspec init --tools qwen
openspec config profile
```

В профиле включите расширенный workflow с командами `/opsx:new`,
`/opsx:continue` и `/opsx:verify`.

### 2. Скопируйте файлы набора

Перенесите в корень проекта:

```text
.qwen/agents/
openspec/schemas/analysis-driven/
openspec/config.example.yaml
AGENTS.md
```

Если в проекте уже есть `AGENTS.md`, объедините правила, не удаляя существующие
инструкции проекта.

### 3. Настройте OpenSpec

Объедините `openspec/config.example.yaml` с `openspec/config.yaml`. Минимальная
конфигурация:

```yaml
schema: analysis-driven

context: |
  Рабочий язык требований: русский.
```

Используйте:

- `context` для коротких стабильных сведений о продукте и проекте;
- `rules.<artifact-id>` для дополнительных правил конкретного артефакта;
- `operations` для проектных указаний на apply и archive.

Пример:

```yaml
rules:
  system_requirements:
    - Новые HTTP API должны соответствовать docs/api-conventions.md.
  test_cases:
    - Для критичных пользовательских сценариев использовать тег smoke.
```

Не копируйте в config общие правила аналитики или структуру документов: они уже
заданы субагентами, схемой и шаблонами.

### 4. Обновите и проверьте установку

```bash
openspec update
openspec schema validate analysis-driven
openspec schema which analysis-driven
```

`schema which` должен показать схему из текущего проекта. Перезапустите Qwen Code,
проверьте субагентов через `/agents manage` и убедитесь, что доступна команда
`/opsx:continue`.

## Первый change

Если задача ещё не определена:

```text
/opsx:explore
```

Создайте change:

```text
/opsx:new add-example-feature
```

Затем повторяйте:

```text
/opsx:continue add-example-feature
```

Каждый вызов создаёт один следующий артефакт и останавливается. OpenSpec выбирает
артефакт по зависимостям схемы.

После создания `tasks.md`:

```text
/opsx:apply add-example-feature
/opsx:verify add-example-feature
/opsx:sync add-example-feature
/opsx:archive add-example-feature
```

`sync` можно пропустить, если delta specs будут синхронизированы во время archive.

## Как проходит работа с субагентом

Для `business-requirements.md`, `system-requirements.md` и `test-cases.md` основной
агент:

1. Передаёт владельцу артефакта upstream-документы, шаблон, project context и rules.
2. Передаёт пользователю вопросы субагента, а ответы возвращает тому же субагенту.
3. Показывает пользователю полный проект артефакта.
4. После согласования просит владельца самостоятельно записать файл.

Основной агент не редактирует ролевые файлы и не принимает решения за пользователя.
Предложение модели или best practice не становится требованием без подтверждённого
источника.

Артефакт создаётся после предусмотренного анализа и, когда требуется, согласования.
Поэтому наличие файла означает его готовность для зависимых этапов.

## Блокирующие вопросы

Вопросы хранятся как `BQ-*`, `SQ-*` или `QA-Q-*`.

- Открытый вопрос со значением `Блокирует: Да` останавливает downstream-этапы.
- У вопроса со статусом `Resolved` должно быть заполнено поле `Ответ / решение`.
- Неблокирующий вопрос может остаться открытым, если он не мешает продолжению.

Если меняется смысл upstream-артефакта, затронутые downstream-артефакты нужно
пересмотреть в порядке зависимостей. Ролевой файл обновляет только его владелец.

## Граница ответственности

| Слой | Содержимое |
|---|---|
| `.qwen/agents/*.md` | Метод работы роли, источники и профессиональные ограничения. |
| `schema.yaml` | Цель артефакта, зависимости, оркестрация и критерии готовности. |
| `AGENTS.md` | Поведение основного агента при `/opsx:continue`. |
| `templates/*.md` | Структура и обязательные поля сохраняемого документа. |
| `config.yaml` | Контекст и дополнительные правила конкретного проекта. |

Если правило остаётся верным при переносе набора в другой проект, оно относится к
роли, схеме или шаблону. В `config.yaml` помещайте только то, что зависит от проекта.

## Трассировка

Основная цепочка:

```text
BR → AC → SR/NFR → OpenSpec Requirement + SC → TC → TASK
```

| ID | Значение |
|---|---|
| `BR-*` | Бизнес-требование. |
| `AC-*` | Критерий приёмки. |
| `BQ-*` | Открытый бизнес-вопрос. |
| `SR-*` | Системное требование. |
| `NFR-*` | Измеримое нефункциональное требование. |
| `SQ-*` | Открытый системный вопрос. |
| `SC-*` | Сценарий OpenSpec Requirement. |
| `TC-*` | Тест-кейс. |
| `QA-Q-*` | Вопрос, мешающий определить проверку или ожидаемый результат. |
| `TASK-*` | Задача реализации или проверки. |

ID не перенумеровываются и не переиспользуются. Связи между элементами указываются
через `Refs` или поле источника.
