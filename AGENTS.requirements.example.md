# Оркестрация аналитических субагентов

## Обязательная последовательность

1. При изменении цели, scope, ролей, процесса, бизнес-правил, функционального поведения или критериев приемки сначала вызови `business-analyst`.
2. После актуализации `business-requirements.md` вызови `system-analyst` для обновления `system-requirements.md`.
3. После актуализации системных требований обнови OpenSpec delta specs и `design.md`.
4. После готовности specs и design вызови `qa-engineer` для создания или обновления `test-cases.md`.
5. Только после этого обновляй `tasks.md` и переходи к реализации.

## Владение файлами

- `business-analyst` изменяет только `openspec/changes/<change-id>/business-requirements.md`.
- `system-analyst` изменяет только `openspec/changes/<change-id>/system-requirements.md`.
- `qa-engineer` изменяет только `openspec/changes/<change-id>/test-cases.md`.
- Ни один из них не изменяет код, автоматические тесты, specs, design или tasks.
- Основной агент отвечает за согласованность между аналитическими документами, specs, design, test cases и tasks.

## Конфликты

- Техническое ограничение, меняющее бизнес-смысл, возвращается `business-analyst` как открытый вопрос.
- Бизнес-изменение, влияющее на систему, требует повторного запуска `system-analyst`.
- Изменение требований, specs или design требует повторного запуска `qa-engineer` для анализа влияния на тест-кейсы.
- QA Engineer не определяет ожидаемое поведение при конфликте, а возвращает вопрос владельцу исходного требования.
- Не исправляй конфликт молча и не допускай параллельного редактирования одного файла двумя агентами.
